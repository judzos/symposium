LLM Agent

A system in which a language model controls the process: it decides what to do next, calls tools, and carries state across steps.

flowchart TD
  S[Agentic system] --> W[Workflow — a human wrote the code paths]
  S --> A[Agent — the model directs its own process]
  A --> P[LLM as policy]
  A --> C[Context as observation space]
  A --> T[Tools as action space]
  P --> PL[Planning — decomposition, reflection, refinement]
  C --> M1[Short-term — in-context, bounded by the window]
  C --> M2[Long-term — an external vector store, retrieval renamed]
  T --> TU[Tool use — the hard part is knowing when and how]
  PL --> R[ReAct — thought, action, observation interleaved]
  R --> RF[Reflexion — detect an inefficient trajectory and reset]

In short

  • A workflow follows code paths a human wrote; an agent directs its own process, and the two fail differently.
  • Agent = LLM + Context + Tools maps onto policy, observation space and action space.
  • Weng’s components are planning, memory and tool use; knowing when and how to call a tool is the hard part.
  • Reflection-style loops make trial and error possible, while long-horizon planning stays brittle.
  • Multi-agent failures are design flaws: simple fixes gained ChatDev only 15.6%.

Two definitions, and the argument between them

Following Anthropic’s framing, there are two kinds of agentic system1:

  • Workflow — LLMs and tools orchestrated through code paths a human wrote.
  • Agent — the LLM directs its own process, deciding how to use tools and sequence work.

They fail in different ways and require different evaluations. Much disagreement about “agent reliability” comes from people describing different architectures.

agent-control-boundary makes this a continuum rather than a label: a system can leave retrieval or tool choice to the model while keeping permissions, termination, and other transitions deterministic.

What separates a workflow from an agent?

Who chose the control flow. In a workflow a human wrote the code paths the model and tools move through; in an agent the model directs its own process and sequences the work.

One formula, two decompositions

AI Agents in Depth: Design Principles and Engineering Practice2 compresses the whole object to Agent = LLM + Context + Tools and maps its parts as LLM ↔ policy, Context ↔ observation space, Tools ↔ action space. In this formulation, an agent is a reinforcement learning agent whose policy happens to be a language model.

What is the reinforcement-learning reading of Agent = LLM + Context + Tools?

LLM ↔ policy, Context ↔ observation space, Tools ↔ action space. It makes an LLM agent an RL agent whose policy happens to be a language model, rather than a slogan.

That formula and Weng’s three components below describe the same decomposition at different levels. Li’s Context absorbs Weng’s memory, while planning becomes part of the policy rather than a separate component. The production form adds three safeguards: Agent = Model + Harness, covered under harness-engineering.

Three components

LLM Powered Autonomous Agents3 supplies the decomposition the field settled on:

Planning covers subgoal decomposition, reflection, and refinement. Chain of Thought spends test-time compute breaking a task into steps. Tree of Thoughts generates several thoughts per step and searches the resulting tree (BFS or DFS, states scored by a classifier or majority vote). LLM+P outsources planning entirely to a classical PDDL planner, translating in and out of natural language.

Memory has two forms: short-term memory is in-context learning, bounded by the context window; long-term memory is an external vector store queried at retrieval time, which is Retrieval-Augmented-Generation under another name. Weng maps these onto human memory (sensory / short-term / long-term) and calls the mapping a rough analogy.

Tool use calls external APIs for what is not in the weights. MRKL routes queries to expert modules, neural or symbolic. TALM and Toolformer finetune the model to call APIs. HuggingGPT uses the LLM as a task planner selecting HuggingFace models across four stages. tool-interface-design separates access from reliability: schemas, validation, bounded permissions, useful errors, and result formatting determine whether the agent can understand and recover from a failed call.

What distinguishes an agent's short-term memory from its long-term memory?

Short-term is in-context learning, bounded by the context window. Long-term is an external vector store queried at retrieval time — which is retrieval-augmented generation under another name.

MRKL found that knowing when and how to use a tool is harder than operating the tool. Their 7B model could not extract arguments for basic arithmetic from a verbal problem with consistency, though it had access to a calculator that worked without error.

What did MRKL's arithmetic failure show about tool use?

That the hard part is knowing when and how to call a tool, not the tool itself. Their 7B model could not reliably extract the arguments from a verbal problem even though the calculator it needed was available and perfectly reliable.

Self-reflection is what makes trial and error possible

ReAct interleaves Thought / Action / Observation and beats an act-only baseline on both knowledge-intensive and decision-making tasks, showing the value of the reasoning trace. Reflexion adds a heuristic that detects inefficient trajectories and hallucination, using a run of identical actions that produce identical observations as its operational definition, and can reset the environment to start a fresh attempt. reflection-evaluator-loop generalises the pattern to generate, critique, externally test, and revise; an executable check or separate evaluator can catch what self-critique misses.

How does Reflexion detect hallucination operationally?

As a run of identical actions producing identical observations. The agent is repeating itself and learning nothing, which is a signal available without knowing what the right answer was. Chain of Hindsight conditions on a sequence of past outputs annotated with feedback and ranked by reward.

Four design patterns

The workflow patterns are Reflection (the agent evaluates and revises its own output; the simplest pattern and consistently effective), Tool Use, Planning, and Multi-agent Collaboration (distinct roles contributing specialised work)1. single-vs-multi-agent-economics supplies a selection rule: add agent boundaries only when parallelism, specialization, or independent verification repays their latency, serialization, information loss, and governance cost.

The protocol layer

An agent has two connection boundaries (agent-protocol-layer): MCP standardises how a model application reaches tools and data, while A2A describes discovery, tasks, messages, and artifacts between agents. Neither protocol supplies correctness, permissions, or competent tool choice by itself.

Three limits Weng names

  • Finite context length: vector stores extend reach, but their representational power is weaker than full attention.
  • Brittle long-horizon planning: LLMs struggle to revise a plan after an unexpected error, where humans learn from trial and error.
  • Natural language is an unreliable interface: the model may produce malformed output or decline to follow an instruction, which is why so much agent code is output parsing.

Why doesn't a vector store simply solve the finite-context limit?

Its representational power is weaker than full attention. Retrieval extends reach but does not give the model the same access to the retrieved material that having it in context would.

What does long-horizon planning break on?

Revising a plan after an unexpected error. Trial and error is where humans learn most, and it is the case LLM planners handle worst.

Multi-agent failure is structural

The 2025 MAST study2 examined ~150 execution traces across MetaGPT, ChatDev, AG2 and Magentic-One, human-annotated at κ = 0.88. It found 14 failure modes in three groups: system design flaws, inter-agent alignment failures, and missing task verification. Simple fixes gained ChatDev only 15.6%, leading the authors to classify the failures as design flaws rather than bugs.

This evidence qualifies the multi-agent collaboration pattern in Primers • Agents1: current implementations fail for reasons that patches do not resolve.

What made MAST conclude multi-agent failures are design flaws rather than bugs?

Simple fixes bought ChatDev only 15.6%. The 14 failure modes cluster into system design, inter-agent alignment and missing verification — categories patching does not reach.
